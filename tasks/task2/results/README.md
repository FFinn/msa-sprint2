# Задание 2

## Что реализовано

В этой итерации публичный REST-контракт монолита сохранён, но операции бронирования
передаются в новый gRPC-сервис `booking-service` через предоставленный компонент-посредник в монолите.

- `POST /api/bookings` идёт через монолит и создаёт запись в `booking-service`;
- `GET /api/bookings?userId=...` идёт через монолит и читает данные из `booking-service`;
- `booking-service` стал новым владельцем данных бронирований;
- Kafka используется только для асинхронного события `BookingCreated`;
- `booking-history-service` строит отдельную аналитическую модель чтения и не является
  источником истины для чтения бронирований в промышленной среде.

Хотя в формулировке задания 2 есть упрощённая фраза, что GET "работает как раньше",
в этом решении и `POST`, и `GET` проходят через gRPC-компонент-посредник. Это сделано намеренно и
согласовано с решением задания 1: после переключения у бронирований один владелец данных,
поэтому нельзя оставлять запись в новой БД, а чтение в старой.

Ограничение текущего учебного стенда: предоставленный JAR монолита не преобразует
gRPC `FAILED_PRECONDITION` в HTTP `4xx` на REST-фасаде. Поэтому ошибочные
`POST /api/bookings` через монолит сейчас возвращают обобщённый HTTP `500`, хотя
прямая gRPC-проверка показывает корректную бизнес-ошибку `FAILED_PRECONDITION`.
Это зафиксировано как ограничение компонента-посредника, а не `booking-service`.

## Архитектура перехода

На этом этапе монолит остаётся внешним REST-фасадом, а внутренняя логика бронирования
переезжает в новый сервис:

1. Монолит принимает REST-запрос.
2. Компонент-посредник `grpcBookingService` вызывает `booking-service` по gRPC.
3. `booking-service` выполняет синхронные проверки через REST в монолит:
   активность пользователя, наличие в чёрном списке, статусы `operational`, `trusted` и `fully-booked` отеля,
   VIP-статус и применимость промокода.
4. После успешной проверки `booking-service` записывает бронирование в свою БД и в
   той же транзакции пишет событие в `booking_outbox`.
5. Фоновый компонент-публикатор отправляет `BookingCreated` в Kafka.
6. `booking-history-service` читает Kafka и формирует свою таблицу `booking_history`.

## Стратегия переноса данных в промышленной среде

В промышленной среде миграция должна идти так:

1. Одноразово перенести исторические бронирования из БД монолита в `booking-db`.
2. Сверить количество записей, ключи и контрольные суммы.
3. Выполнить короткую остановку или применить финальную дельту перед переключением.
4. Только после этого одновременно включить компонент-посредник и для чтения, и для записи.
5. Возврат на прежнее состояние допустим только до переключения. Нельзя оставлять запись в одной БД,
   а чтение в другой.

Тестовые наборы данных в `monolith-db` и `booking-db` используются только для
изолированного автотеста задания 2. Это не перенос данных для промышленной среды.

## Запуск

```bash
cd tasks/task2
docker network inspect hotelio-net >/dev/null 2>&1 || \
  docker network create hotelio-net
docker compose down --volumes --remove-orphans
docker compose up -d --build
./collect-results.sh
```

## Что лежит в каталоге `results`

- `docker-ps.txt` — состояние контейнеров после запуска;
- `test-log.txt` — полный реальный лог проверки;
- `monolith-bookings.json` — список бронирований через REST монолита;
- `grpc-bookings.txt` — список бронирований через прямой gRPC-вызов;
- `monolith-booking-db.txt` — содержимое старой таблицы `booking` в монолите;
- `booking-db.txt` — содержимое новой таблицы `bookings`;
- `booking-history-db.txt` — содержимое асинхронной таблицы `booking_history`;
- `monolith-logs.txt` — фрагмент логов монолита с `bookingService` и `grpcBookingService`.
